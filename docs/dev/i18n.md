# Languages in the code

What a person sees about languages, and how to improve a translation, is in
[Morse in your language](../i18n.md). This is how it works in the code.


- `core/i18n.js` has `t(id, vars, lang)`, the language lists and detection
  (`pickLanguage` for browsers, `languageFromEnv` for the terminal). It has
  no dependencies besides the English catalog. The runtime bundle inlines it
  first (`runtime/bundle.js`); extension pages and the share page import it,
  and `extension/i18n-page.js` fills in elements marked `data-i18n`,
  `data-i18n-html` and `data-i18n-attr`.
- Only English is built in. Every other language is loaded when it is
  chosen: `setLanguage(await loadLanguage(code))`. `setLanguage` only
  switches to a language whose words are here (else English), so nothing
  ever shows a message id. Where the words come from is set once with
  `setLanguageLoader`:
  - the extension's worker and pages: `extension/words.js` reads
    `locales/<code>.json` from the package (`scripts/build.js` writes them;
    they are not web-accessible);
  - the in-page runtime: `runtime/src/04-i18n.js` asks its host with
    `i18n.words` (the worker, the desktop connector, or a demo page's fake
    host) and `97-boot.js` waits for the answer (1.5 s at most) before the
    overlay first shows;
  - the CLI, the desktop connector, tests and the website: importing
    `core/languages.js` reads `core/locales/<code>.js`.
  `tests/i18n-lazy.test.js` checks that no bundle carries another
  language's words, and that German and Persian still show in the real
  extension and over CDP.
- In the runtime, `runtime/src/04-i18n.js` follows the Language setting,
  sets `dir` and `lang` on the shadow host, and repaints what is showing
  (`tBind`, `langSubs`). Labels that are built once use getters or small
  functions so they read the current language.
- Text the model reads stays English: pass `"en"` as the language, as in
  `t(id, {}, "en")` and `stepWords(step, "en")`.
- The overlay's CSS uses logical sides (`inset-inline-start`,
  `padding-inline`, `text-align: start`). Arrows that mean "forward" and the
  undo and redo icons mirror in right-to-left languages; key caps stay left
  to right.
- Host code (`core/pack.js`, `core/gallery.js`, `core/style.js`,
  `core/backup.js`, `core/providers.js`, `extension/background.js`, the
  `daemon/` commands) imports `t` too. The extension's worker follows the
  Language setting (`followLanguage` in `background.js`); the terminal
  follows `LANG` (`daemon/cli.js`). An error that is already in the
  person's words is thrown with `plain: true` so `plainError` passes it
  through.
- Names for parts of a page ("Section", "Button") are `kind.*` messages.
  `describe(el, lang)` in `runtime/src/20-context.js` uses them; the page
  context sent to the model calls it with `"en"`.
- `tests/words.test.js` checks the English catalog for jargon, the same way
  it checks the source.
- `tests/i18n-strings.test.js` fails when the runtime shows English that
  doesn't go through `t()`. It scans `runtime/src` and `runtime/boot.js` for
  sentences, words between tags, `title` / `aria-label` / `placeholder` /
  `alt` values and literals passed to `announce`, `toast` and similar. A
  string that stays English on purpose goes in its `ALLOWED` list with the
  reason.
